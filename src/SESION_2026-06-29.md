### 2. Extendimos el ETL para procesar carpetas completas

El `main.py` original solo procesaba un archivo a la vez. Lo extendimos con dos funciones nuevas:

**`process_folder(input_dir)`**  
Lee todos los archivos `.json` de un directorio, ejecuta el pipeline completo en cada uno, y devuelve un único DataFrame consolidado con todas las tareas. Si un archivo falla (JSON malformado, por ejemplo), lo registra como error y sigue con los demás — el batch no se detiene.

**`save_partitioned_parquet(df, output_dir, partition_cols)`**  
Escribe el DataFrame en formato Hive-particionado. Esto significa que en lugar de un solo archivo plano, se genera una estructura de directorios:

```
data/parquet/evaluation/
  split=train/
    task_id=00576224/  ← aquí viven las filas de entrenamiento de esa tarea
  split=test/
    task_id=00576224/  ← aquí viven las filas de test de esa tarea
```

**Por qué particionamos por `split` primero y `task_id` segundo:**  
El caso de uso más frecuente del pipeline de inferencias es "dame todos los inputs de test" — eso requiere leer solo `split=test/` y saltar completamente el directorio `split=train/`. Si hubiéramos puesto `task_id` primero, ese filtro no podría evitar abrir los 400 directorios de tareas. El orden de partición importa.

### 4. Agregamos `source_path` al schema

Al analizar el Parquet generado, detectamos que faltaba un campo que el `schema_contracts.md` del proyecto listaba como requerido: `source_path` — la ruta al archivo JSON original que generó esa fila.

Sin este campo, si una fila tiene un problema, no puedes rastrear de qué archivo vino sin hacer una búsqueda manual. Con él, cada fila es autocontenida: sabe de dónde viene.

El cambio fue pasar la ruta del archivo desde `process_folder` hacia `transform_task_to_rows`, que ya lo recibía como parámetro y lo añadía a cada fila. *(Actualización posterior: `_source_path_for_row()` normaliza la ruta como POSIX relativa al repo; ver `agent_context/conventions/schema_contracts.md`.)*

### 5. Creamos el snippet para el compañero de inferencias (`notebooks/inference_input_reader.py`)

El Parquet está en formato largo: una fila por grid. Para construir un prompt de inferencia necesitas reconstruir la estructura completa de una tarea (pares input/output de entrenamiento + el input de test). Eso requiere saber cómo filtrar y pivotar el DataFrame.

Creamos un archivo en `notebooks/` que tu compañero puede ejecutar directamente. Tiene 5 secciones:

1. **Cargar el dataset completo** — una línea con `pd.read_parquet`
2. **Listar las tareas disponibles** — qué task_ids hay
3. **`load_task(df, task_id)`** — función lista para usar que reconstruye un dict `{train: [...], test: [...]}` exactamente en el formato que un builder de prompts espera
4. **Esqueleto del loop de inferencia** — cómo iterar todas las tareas
5. **Filtros rápidos útiles** — solo inputs de test, tareas con grids grandes (útil para ajustar la ventana de contexto del modelo)

### 6. Congelamos el schema del Parquet

A partir de esa semana, cambiar columnas sin aprobación del equipo estaba prohibido. Para hacer eso cumplible técnicamente (no solo como política), agregamos dos cosas al código:

**`TASKS_PARQUET_SCHEMA`** — una constante en `main.py` que declara las 15 columnas autorizadas y si cada una puede tener NULLs o no.

**`validate_output_schema(df, schema)`** — una función que corre **antes** de cualquier escritura a disco y falla con error explícito si detecta:
- Una columna extra que no está en el schema aprobado
- Una columna que desapareció
- Un NULL en una columna que no debería tenerlo

Probamos los tres casos con datos sintéticos para confirmar que el guard funcionaba. El mensaje de error dice exactamente qué está mal:

```
Schema violation:
  - Unexpected columns (need approval to add): ['model_id']
```

Esto significa que si alguien del equipo de inferencias intenta meter `model_id` en el Parquet de tareas (que es el Parquet equivocado para ese campo), el ETL falla antes de escribir nada.

### 7. Garantizamos reproducibilidad bit a bit

El problema: si borrabas el Parquet y lo regenerabas, el resultado no era idéntico. La causa era `ingested_at`, que usaba `datetime.now()` — un valor diferente en cada ejecución.

La solución: en lugar de capturar cuándo corrió el ETL, capturamos cuándo fue modificado por última vez el archivo fuente:

```python
file_mtime = datetime.fromtimestamp(
    file_path.stat().st_mtime, tz=timezone.utc
).isoformat()
```

Este valor es estable mientras el JSON no cambie. Si ARC-AGI actualiza un archivo de tarea, el mtime cambia y `ingested_at` cambia también — lo que es correcto: indica que esa fila viene de una versión más nueva del dato.

**Verificación:** Corrimos el ETL dos veces seguidas, borrando el Parquet entre ejecuciones, y comparamos el MD5 de cada archivo generado. Resultado: idénticos en ambas corridas.
